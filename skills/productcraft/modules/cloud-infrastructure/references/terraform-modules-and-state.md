# Terraform: modules, state and refactoring without recreation

Read this when you design or change a reusable module, split a monolithic configuration, rename or move resources, change `count` to `for_each`, set up or migrate a backend, organize environments, or deal with drift. Style rules are in `terraform-style.md`.

State maps configuration addresses to real objects. Most expensive Terraform mistakes are state mistakes: an address changes and Terraform plans to destroy the old object and create a new one. Every refactor in this file ends with a plan that shows moves only.

## When a module earns its place

- **Write one** for a group of resources that share a lifecycle and are deployed more than once (a service's network, a standard bucket with its policy, encryption and logging), or to enforce a company standard.
- **Do not write one** around a single resource without adding policy, or to "organize" code used once. A thin wrapper adds a version to maintain and an interface to keep compatible, and gains nothing.
- **Prefer composition** over deep nesting. A root module calls a few focused modules and wires their outputs together. Nesting beyond one level makes plans hard to read and refactors hard to do.
- Before writing a module, check whether a maintained public module already does the job (for Azure, see `azure-verified-modules.md`). Read its code and pin its version like any dependency.

## Designing the interface

- Few required inputs, safe defaults for the rest. Secure by default: encryption on, public access off, logging on, deletion protection on for data stores.
- Typed object inputs with `optional()` attributes beat dozens of flat variables, but avoid one giant `config` object of type `any`; it defeats validation.
- No `provider` blocks inside the module (only `required_providers` and `configuration_aliases`). A module with its own provider block cannot be used with `count` or `for_each` and cannot be removed cleanly.
- No module-wide `enabled` flag; callers use `count` or `for_each` on the `module` block. Feature flags for optional sub-resources are fine.
- Outputs expose IDs and attributes callers need, as discrete values or maps keyed like the inputs.
- Document with a README generated by terraform-docs and at least one runnable example under `examples/`.

### What counts as a breaking change

Release modules with semantic versions. Treat these as breaking (major version) unless a `moved` block or default keeps old callers working:

- Removing or renaming a variable or output; changing a variable's type; adding a required variable; changing a default in a way that changes existing infrastructure.
- Renaming a resource, switching `count` and `for_each`, or moving resources between modules without `moved` blocks.
- Adding a resource that every existing caller would get on upgrade. In a minor release, put new resources behind a toggle that defaults to off.
- Raising the minimum provider or Terraform version.

## Sources and pinning

```hcl
module "network" {
  source  = "app.terraform.io/acme/network/aws"   # registry: use the version argument
  version = "~> 3.2"
}

module "logging" {
  source = "git::https://example.com/platform/tf-modules.git//logging?ref=v1.4.0"  # git: pin ref, no version argument
}
```

- The `version` argument works only for registry sources. For git sources pin `ref` to a tag, or to a commit SHA when tags can move.
- Production root modules pin exact or tightly constrained versions; upgrade in a reviewed change with a plan.
- `terraform get -update` or `init -upgrade` changes what is fetched; review the plan afterwards.

## Organizing environments and state

- **Split state by lifecycle, ownership and blast radius.** Network, data stores and application layers change at different speeds and need different reviewers. One state per environment per layer is a common shape. A smaller state means faster plans and smaller accidents.
- **Directories per environment** (`envs/prod`, `envs/staging`, each a small root module calling shared modules with its own backend key) make the target obvious in every command and every review. CLI workspaces share one configuration and switch state invisibly; use them for short-lived copies (feature environments), not for prod versus dev.
- **Share values between states** through outputs read with a data source the consumer is allowed to read (an SSM parameter, a Key Vault secret, a tag lookup) or `terraform_remote_state`. The latter grants read access to the whole producer state, secrets included, so use it only where that access is already acceptable.

## Backends

| Backend | Locking | Must also have |
|---|---|---|
| S3 | `use_lockfile = true` (S3 conditional writes; experimental in 1.10, generally available in 1.11). DynamoDB locking still works but is deprecated | Versioning on the bucket, encryption (SSE-KMS), public access blocked, access limited to the deploy roles |
| `azurerm` | Blob lease, automatic | Soft delete and versioning on the container, Entra ID auth (`use_azuread_auth`), no shared access keys where avoidable |
| `gcs` | Automatic | Object versioning, uniform bucket-level access, restricted IAM |
| HCP Terraform or Terraform Enterprise | Automatic | Workspace permissions, run approvals, sentinel or OPA policies if used |

```hcl
terraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

- State and saved plan files contain every attribute in clear text, including secrets. Treat read access to the bucket as read access to those secrets.
- Keep environment-specific backend settings out of the code with partial configuration (`terraform init -backend-config=backend/prod.hcl`) when one configuration serves several environments.
- Migrating backends (`terraform init -migrate-state`) and `terraform force-unlock` change shared state. Ask first. Before a force-unlock, confirm no plan or apply is still running (CI, a colleague) and record the lock ID you are removing.

## Refactoring with `moved`, `removed` and `import`

`moved` blocks (Terraform 1.1+) record that an address changed, so the next plan moves state instead of replacing objects. They are code: reviewed, versioned and applied by everyone who uses the configuration.

```hcl
# Monolith to module, and count to for_each, in one reviewed change
moved {
  from = aws_vpc.main
  to   = module.network.aws_vpc.this
}

moved {
  from = aws_subnet.private[0]
  to   = module.network.aws_subnet.private["eu-west-1a"]
}

moved {
  from = aws_subnet.private[1]
  to   = module.network.aws_subnet.private["eu-west-1b"]
}
```

| Situation | Tool |
|---|---|
| Rename a resource or module call; move into, out of or between modules in the same state; `count` to `for_each` | `moved` block |
| Stop managing a resource but keep it running | `removed { from = aws_x.y  lifecycle { destroy = false } }` (1.7+), instead of `terraform state rm` |
| Move a resource to a different state | `removed` with `destroy = false` in the old configuration, `import` block in the new one, applied in that order |
| A provider changed a resource type (for example a split resource) | The provider's documented `moved` support (`ResourceWithMoveState`, 1.8+) or `removed` plus `import` |

Rules that keep refactors safe:

1. Make the refactor its own change, with no behavior change mixed in (`../../engineering-practices/references/large-refactors.md`).
2. Write the `moved` blocks, run `terraform plan -out=tfplan`, and check that every line says "has moved to" and the summary is `0 to add, 0 to change, 0 to destroy`. Run `python3 <productcraft>/modules/cloud-infrastructure/scripts/plan_review.py --expect-no-changes plan.json` on the JSON form; any HIGH finding means an address did not match.
3. Plan every environment and workspace that uses the configuration, not just one.
4. In shared modules, keep `moved` blocks for at least one major version so callers on old versions can upgrade. In a root module you may delete them once every state that uses it has been applied.
5. `terraform state mv` does the same job imperatively, but leaves no record and does not reach other environments. Use it only when `moved` cannot express the change, with a backup (`terraform state pull > before.tfstate`, stored as securely as the state) and the user's approval.

## Drift

- `terraform plan -refresh-only` shows what changed outside Terraform without proposing changes. `terraform apply -refresh-only` writes those observations into state; it is a state change and needs approval. `terraform refresh` is deprecated.
- For each drifted attribute decide: put the real value into code (someone changed it for a reason), or let the next apply restore the coded value. Ask the owner when the reason is unclear.
- Recurring drift on one attribute usually means another system owns it (an autoscaler, a tag policy, a controller). Hand ownership to one side and use a narrow `ignore_changes` with a comment.

## Done when

- [ ] The module interface is typed, documented, secure by default and contains no provider configuration.
- [ ] Sources are pinned (registry `version` or git `ref`), and any breaking change is released as a major version.
- [ ] State is remote, locked, encrypted, versioned and access-restricted; no state or plan file is committed.
- [ ] Refactors produced a plan with moves only in every affected environment, and `plan_review.py --expect-no-changes` reported no HIGH findings.
- [ ] Every state-changing command (`state mv`, `state rm`, `force-unlock`, `-migrate-state`, `apply -refresh-only`) ran only after the user approved it.

## Pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| Refactor plan shows destroy and create | A `moved` address does not match exactly (index, key, module path) | Copy addresses from `terraform state list`; quote keys exactly |
| "Moved object still exists" | Old and new addresses both exist in configuration | Remove the old block from configuration |
| `version` argument rejected | Used with a git or local source | Pin `ref` in the URL instead |
| Lock never released after a crashed run | Process killed mid-operation | Confirm nothing runs, then `force-unlock LOCK_ID` with approval |
| One `apply` touches every environment | Shared state or workspaces used for prod and dev | Separate backends per environment and layer |
