# Terraform Stacks

Read this when a repository contains `.tfcomponent.hcl` or `.tfdeploy.hcl` files, or the user wants to deploy the same set of components to many environments, regions or accounts through HCP Terraform.

Stacks became generally available in HCP Terraform in 2025 and need Terraform 1.13 or later for the `terraform stacks` commands. They are an HCP Terraform feature: OpenTofu and plain CLI backends do not run them, and resources managed through Stacks count toward HCP Terraform billing. Features and limits are still moving, so check the current documentation and the installed version (`terraform stacks version`) before relying on any detail here.

## When Stacks fit

- **Fit:** one set of components (network, cluster, application) deployed repeatedly with different inputs, with dependencies between components, including values only known after apply (a cluster endpoint feeding Kubernetes resources). Stacks plan and apply components in dependency order and can defer the parts that depend on unknown values to a later step.
- **Do not fit:** a single environment, a team not on HCP Terraform, or infrastructure already well served by a few root modules and workspaces. Migrating means new state per deployment; plan it as a migration, not a refactor.

## Files

| File | Holds |
|---|---|
| `*.tfcomponent.hcl` | `variable`, `required_providers`, `provider`, `component`, `output`, `locals`, `removed` |
| `*.tfdeploy.hcl` | `identity_token`, `deployment`, `deployment_group`, `deployment_auto_approve`, `store`, `locals`, `publish_output`, `upstream_input` |
| `.terraform.lock.hcl` | Provider hashes, generated by `terraform stacks init` or `providers-lock`; commit it |
| `.terraform-version` | The Terraform version for the Stack |

All of them sit at the root of the Stack's directory. Components point at ordinary modules (local paths, registry or git sources) that must not contain `provider` blocks.

## A minimal Stack

```hcl
# components.tfcomponent.hcl
required_providers {
  aws = { source = "hashicorp/aws", version = "~> 6.0" }
}

variable "region"         { type = string }
variable "role_arn"       { type = string }
variable "identity_token" {
  type      = string
  ephemeral = true                     # never written to state
}

provider "aws" "this" {                # alias is the second label; settings live in config
  config {
    region = var.region
    assume_role_with_web_identity {
      role_arn           = var.role_arn
      web_identity_token = var.identity_token
    }
  }
}

component "network" {
  source    = "./modules/network"
  inputs    = { cidr = "10.20.0.0/16" }
  providers = { aws = provider.aws.this }
}

component "app" {
  source    = "./modules/app"
  inputs    = { subnet_ids = component.network.private_subnet_ids }   # dependency inferred
  providers = { aws = provider.aws.this }
}

output "app_url" {
  type  = string                       # outputs require a type
  value = component.app.url
}
```

```hcl
# deployments.tfdeploy.hcl
identity_token "aws" {
  audience = ["aws.workload.identity"]
}

deployment "staging" {
  inputs = {
    region         = "eu-west-1"
    role_arn       = "arn:aws:iam::111122223333:role/stacks-staging"
    identity_token = identity_token.aws.jwt
  }
}

deployment "production" {
  inputs = {
    region         = "eu-west-1"
    role_arn       = "arn:aws:iam::444455556666:role/stacks-production"
    identity_token = identity_token.aws.jwt
  }
}
```

Differences from ordinary Terraform that trip people up: Stack variables need a `type` and do not accept `validation` (validate inside the modules); providers take their settings in a `config` block and may use `for_each`; outputs need a `type`; deployments cannot use `count` or `for_each`; local module paths must be relative.

## Authentication

Use workload identity: an `identity_token` block in the deployment file, a cloud role or federated credential that trusts HCP Terraform, and a trust condition narrowed to the organization, project, Stack and deployment. One role per deployment keeps staging tokens from touching production. Pass tokens through `ephemeral` variables. Variable sets read with a `store` block are for values the platform team already manages; do not move long-lived keys into them to avoid setting up identity.

## Working safely

```bash
terraform stacks init            # providers and modules, lock file
terraform stacks fmt
terraform stacks validate        # local, no upload
terraform stacks providers-lock  # add platform hashes
```

- **`terraform stacks configuration upload` starts deployment runs.** Treat it like a deploy: only with the user's go-ahead, after `validate` passes and the change has been reviewed.
- Approval commands (`deployment-run approve-all-plans`, `deployment-group approve-all-plans`) apply real changes. Never approve a plan the user has not seen.
- `deployment_auto_approve` rules let plans apply without a person. Add or loosen one only when the user asks, keep it on non-production groups, and require at least no removals:

```hcl
deployment_auto_approve "no_deletes" {
  check {
    condition = context.plan.changes.remove == 0
    reason    = "Plans that delete resources need a person."
  }
}

deployment_group "non_production" {
  auto_approve_checks = [deployment_auto_approve.no_deletes]
}
# and in the staging deployment: deployment_group = deployment_group.non_production
```

  Deployment groups and auto-approve rules depend on the HCP Terraform tier, and their wiring has changed between releases (they replaced the older `orchestrate` blocks); confirm the exact syntax in the current documentation and check what the organization's tier allows.
- **Removing a deployment** is a destroy: set `destroy = true` on it, upload, review and approve the destroy plan, and only then delete the block. Each step needs approval. Deleting the block first leaves resources the Stack can no longer reach with credentials.
- **Removing a component** uses a `removed` block with the component's `source` and `providers`, so the Stack can still authenticate to destroy it.
- The `watch` commands stream until interrupted; in automation, poll run status through the HCP Terraform API instead.

## Linked Stacks

A producer Stack exposes values with `publish_output`; a consumer reads them with an `upstream_input` block and `upstream_input.<name>.<output>`. The producer must have applied before the consumer can plan, and a change to a published value triggers runs in consumers. Keep published outputs few and stable, like a module's public interface.

## Done when

- [ ] `terraform stacks validate` and `fmt` pass, and the lock file covers the platforms in use.
- [ ] Every deployment authenticates through workload identity with a role scoped to that deployment.
- [ ] Uploads, approvals, destroys and auto-approve changes happened only with the user's explicit go-ahead.
- [ ] Modules used as components contain no provider blocks and were planned in a non-production deployment first.

## Pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| Upload rejected: variable or output invalid | Missing `type`, or a `validation` block in a Stack variable | Add types; move validation into the module |
| Component fails on a provider error | The module contains a `provider` block | Remove it; pass providers through the component |
| Deferred changes never converge | A dependency cycle or a value that changes every run | Break the cycle, or split into two components or Stacks |
| Consumer Stack cannot read an upstream value | Producer never applied, or output not published | Apply the producer; add a `publish_output` |
| Destroy impossible after deleting a deployment block | Credentials and inputs were removed with the block | Restore the block with `destroy = true`, then follow the removal steps |
